Substrate 学习：快速入门

发表于 2026-11-27 分类于 Go

一个编程智能体可能只工作几分钟，却要等待用户几小时。如果为每个会话保留一个 Pod，空闲进程仍然占着内存；如果直接销毁 Pod，又得考虑工作目录、进程状态和下一次启动。Agent Substrate 从这段等待时间入手：把执行环境保存为快照，释放计算资源，等请求到来时再恢复。Kubernetes 管理一批预先启动的 worker Pod，Substrate 把需要运行的应用分配给它们。

本文通过一个 HTTP 计数器，介绍 Substrate 的部署、访问、暂停与恢复，并观察内存和文件状态如何保留。计数器不调用模型，也不需要 API key，便于把注意力放在执行环境本身。

命令和源码以 Substrate v1.0.0 为基准。实测使用 Linux 6.8、Go 1.27.4 和 Kubernetes 1.36.1，复用了已有的 v1.0.0 Kind 测试集群；下文也列出新建本地集群的步骤。

项目定位

Substrate 提供的是有状态应用的沙箱运行环境。它接受 OCI 镜像，管理启动、暂停、恢复和网络访问。镜像中可以运行智能体、命令行工具或其他应用。本文选用 HTTP 计数器，便于观察请求触发的恢复过程。

项目把这样的应用实例称为 actor。本文的一个计数器就是一个 actor：它有独立的进程内存和文件状态，也有自己的生命周期。

actor 与承载它的 Pod 分开管理。actor 暂停后，其状态保存在快照中，worker 可以接着运行另一个 actor。再次收到请求时，Substrate 从可用 worker 中选择一个恢复它，不必为这次恢复重新创建 Pod。扩充 worker 池时，仍然需要 Kubernetes 调度和启动新的 Pod。

对象与组件

资源对象

先区分几个会出现在命令中的名称：

对象 含义 本文中的例子
Actor 一个有独立状态的应用实例 blog-counter-a、blog-counter-b
ActorTemplate 创建 actor 使用的镜像、资源和快照配置 counter
WorkerPool Substrate 定义的 worker 池配置，通过 CRD 注册到 Kubernetes counter，默认有三个副本
Worker 控制面记录的一个 worker Pod 及其分配状态 实际承载计数器的 worker
Atespace Substrate 中组织资源和授权的范围 ate-demo-counter

这些概念都由 Substrate 定义，但通过两套 API 管理。WorkerPool 通过 CRD（自定义资源定义）注册到 Kubernetes，因此可以用 kubectl 管理。Actor、ActorTemplate 和 Atespace 由 Substrate 自己的 API 管理，用 kubectl ate 操作，数据保存在 PostgreSQL。

WorkerPool 描述池中需要多少个 worker、使用什么沙箱运行时，以及每个 worker 的资源配置。Substrate 的 ate-controller 根据它创建和维护 Deployment，再由 Kubernetes 创建 worker Pod。这里的 Deployment 和 Pod 是 Kubernetes 内置资源，WorkerPool 是 Substrate 对 Kubernetes 的扩展。

这两套 API 管理的对象，最终在 worker Pod 中连接起来。下图左侧是 Substrate 保存的对象，右侧是 Kubernetes 资源；底部展开了 Pod 内的运行层次：

图中的点线表示 Worker 记录与 worker Pod 的对应关系。Worker 记录不属于某个 atespace，它描述 Pod 的位置、容量和分配状态；ateworker 则是 Pod 内操作沙箱的程序。

actor 恢复运行时会被分配给一个 worker。图中的 A 正在运行，B 已暂停，只保留状态和快照引用，之后可以在可用 worker 上恢复。一个 worker Pod 可以同时承载多个独立的 actor 沙箱，数量受资源容量和 actor 数量上限约束；图中只展开了 A。

演示同时使用名为 ate-demo-counter 的 Kubernetes namespace 和 atespace。它们只是名字相同：前者放 worker Pod，后者组织 actor 和模板。

按官方术语表的解释，ate 最初来自 Agent Task / Execution Engine，如今保留为项目的内部命名前缀。kubectl ate 调用的是 kubectl-ate 插件，后面出现的 atelet、atenet 和 ate-system 也沿用了这个前缀。

执行组件

这些对象通过下面的组件连接起来：

ate-api-server 管理 actor 状态、选择 worker，并协调恢复与暂停。每个节点上的 atelet 准备镜像和快照，再通过 RPC 请求 worker 内的 ateworker 操作沙箱。

另外，ate-controller 把 WorkerPool 配置转成 Kubernetes Deployment，维持 worker 数量；atenet-router 负责请求入口。本文使用 gVisor，项目也支持基于 Cloud Hypervisor 的 microVM，两种后端共用上层的 actor 管理接口。

这些名称暂时记住职责即可。接下来的计数器会把它们串起来。

环境准备

本地体验需要 Go、kubectl 和运行中的 rootful Docker。Kind 由仓库脚本通过 Go 管理，不必另行安装。

  • Go 工具链：启用 GOTOOLCHAIN=auto，让 Go 按仓库的模块配置选择工具链。本文实测版本是 Go 1.27.4。
  • Linux 内核：建议沿用本文验证过的 6.8 或更新版本。macOS 需要检查 Docker 所在 Linux 虚拟机的内核，而不是 macOS 版本。
  • 计算资源：为控制面、数据库、对象存储和演示 worker 留出内存与磁盘。官方计数器池默认有三个 worker，每个请求 1 GiB 内存，还需要预留其他组件的资源。
  • 网络条件：构建环境和集群需要访问 Go 模块源、镜像仓库及 gVisor 下载地址。需要代理时，终端、Docker、Kind 节点和 atelet 的出网条件要分别确认。

这里的内核建议与实际文件系统实现有关。镜像缓存代码 使用 overlayfs 的 lowerdir+，代码注明需要 Linux 6.7 及以上，或带相应回移的 6.6.23 及以上内核。因此，不能只凭 Docker 能启动就认定环境满足要求。

本文选择 gVisor，不需要 /dev/kvm。microVM 的本地准备条件见官方开发文档。

空间 含义 本例中的资源 查询方式
Kubernetes namespace Kubernetes 的资源分组，用于组织承载应用的基础设施 WorkerPool、Deployment、worker Pod kubectl -n ate-demo-counter ...
Substrate atespace Substrate 的应用资源分组，也是资源命名与授权的范围 ActorTemplate、Actor kubectl ate ... -a ate-demo-counter

分开管理与两类资源的变化频率有关。worker 池的扩容、Pod 的创建与维护交给 Kubernetes；大量 actor 的创建、调度、暂停和恢复则由 Substrate 自己的控制面处理，状态保存在 PostgreSQL。这样，恢复一个 actor 时可以直接使用已有 worker，减少对 Kubernetes 控制面的依赖。

namespace 和 atespace 没有固定的一一对应关系。本例恰好把它们都命名为 ate-demo-counter，但同名不会自动建立关联。actor 通过 workerSelector 等调度条件选择 worker 池，不同 atespace 中的 actor 也可以共用一个池。

这条部署命令成功返回后，再创建自己的计数器 actor。 首次构建、下载运行时和生成快照通常比后续恢复耗时更长。

网络边界

前面一直通过 proxy 访问计数器，是因为 actor 的网络入口也属于运行环境的一部分。应用镜像里有 HTTP 服务，并不等于它直接暴露在宿主机端口上。

Substrate 使用 gVisor 或 microVM 隔离应用，入口由 atenet-router 处理。出站流量则经过 atenet-egress，按 actor 的 EgressPolicy 决定允许访问哪些目标。本文没有配置外部访问策略，计数器也不需要出网。

以后把计数器替换为调用模型的智能体，还需要补齐允许访问的模型域名、TLS 信任和凭据注入配置。真实密钥可以保存在沙箱外，由出站网关为符合规则的请求替换认证头。具体配置见出站流量和凭据注入指南。

这部分不影响计数器实验，却决定了智能体能访问哪些外部服务。将应用放进沙箱之后，网络权限仍需要单独描述。

故障定位

初次部署出错时，先判断问题发生在哪一层：

现象 优先检查
安装命令停在构建或推送镜像 Go 模块下载、Docker 构建日志、registry 地址与连通性
worker Pod 处于 Pending 节点可用资源和 Pod 的 Events
worker Pod 就绪，actor 仍提示没有容量 kubectl ate get workers 的注册状态、atelet 运行时下载日志、模板的选择条件
模板初始快照未完成 kubectl ate get actor-template counter -a ate-demo-counter -o yaml 中的错误信息
本地 proxy 无法访问 actor router 的入口身份许可、证书签发和 proxy 终端日志

最容易混淆的是“Pod 就绪”和“worker 可以恢复这个 actor”。前者是 Kubernetes 层的状态，后者还取决于运行时和调度条件。kubectl ate get workers 与 atelet 日志可以继续缩小范围。

小结

计数器把 Substrate 的核心过程缩成了几步：通过模板创建 actor，请求到来时恢复，保存快照后释放 worker，下次请求继续原来的状态。模板描述运行条件，控制面安排执行位置，atelet 与 ateworker 操作沙箱，路由把请求交给恢复后的应用。

从这里换成智能体，首先变化的是镜像和应用逻辑。任务编排、空闲判断、模型访问等需求，再分别由上层系统和网络策略补齐。掌握 actor 与 worker 的关系后，这些配置就有了明确的位置。
