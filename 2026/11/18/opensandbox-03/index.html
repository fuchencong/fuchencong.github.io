OpenSandbox 学习 03：沙箱运行时

发表于 2026-11-18

上一篇介绍了 OpenSandbox 的整体架构：管理服务负责准备环境，execd 在环境里执行命令、操作文件。不过，“准备环境”这四个字里还有不少工作。应用指定一个 Python 镜像、CPU 和内存后，究竟是谁创建容器？如果使用 Kubernetes，管理服务和集群控制器又各自做什么？

这些工作由沙箱运行时完成。对应用来说，创建沙箱是一次 API 调用；对运行时来说，它需要把请求变成真正运行的容器或虚拟机，记录环境的状态，并在任务结束后释放资源。同一个沙箱接口能够用于本机和集群，依靠的就是这一层实现。

本文继续沿用订单统计的背景：为任务申请一个 Python 环境，保留几分钟，完成工作后删除。先从 Docker 看最直接的实现，再进入 Kubernetes，重点分析普通 Pod 和预热池两条创建流程，最后介绍暂停恢复，以及 agent-sandbox、Fast Sandbox 的接入方式。

运行时的职责

沙箱与容器

假设应用需要一个装有 Python 的环境，限制为一个 CPU、512 MiB 内存，使用五分钟。这个请求只描述任务需要什么，尚未说明底层怎样完成。使用 Docker 时，这些条件会转换为容器镜像和 Docker 的资源限制。使用 Kubernetes 时，它们会转换为集群资源，再由集群创建或分配 Pod。Pod 是 Kubernetes 承载容器的基本单元，一个 Pod 中可以有多个配合工作的容器。

因此，OpenSandbox 中的 sandbox runtime 可以理解为：负责把沙箱需求落实到底层环境的一组实现。 除了创建，它还要支持查询、删除、续期和暂停恢复等操作。

这里还会遇到另一个含义的 runtime，例如 Docker 使用的 runc，或 Kubernetes 节点上的容器运行时。这些程序负责更底层的容器运行。OpenSandbox 的运行时负责组织整个沙箱的生命周期，两者所在的层次如下：

容器创建

先看本机 Docker。管理服务能够直接访问 Docker Engine，因此可以在一次创建过程中完成镜像准备、容器创建和启动。

状态与清理

创建后的容器带有 OpenSandbox 写入的标签，其中保存沙箱 ID 和初始到期信息。查询沙箱时，管理服务找到对应容器，再把 Docker 状态转换成公共 API 的状态。

Docker 本身不会因为 OpenSandbox 请求中的“五分钟”到了就自动删除容器，因此管理服务需要安排回收。它先把存活时长换算成具体的到期时间。例如，10:00 创建、使用五分钟，就记录为 10:05 到期，再设置定时器触发清理。

  • 记录具体时间，是为了在服务重启后仍然知道沙箱还能使用多久。假设管理服务在 10:03 重启，这个沙箱应当再保留两分钟，而不是重新计时五分钟。如果恢复时已经超过 10:05，就直接触发清理。
  • 续期也需要同时更新清理安排和保存的时间。管理服务先取消旧定时器，按新的到期时间重新安排。Docker 不支持直接修改运行中容器的标签，因此新的时间另外写入本地元数据文件，读取时优先采用这个记录。
  • 定时器只存在于管理服务进程中，进程退出后就会消失。因此，服务启动时会扫描已有沙箱，结合容器标签和本地文件找出各自的到期时间，再重建定时器。管理服务停机期间，容器可能继续运行，已经到期的沙箱会在服务恢复后清理。

主动删除也由 Docker 后端完成：终止容器、删除容器，再清理定时器和相关资源。容器创建或启动失败时，则尝试删除已经创建的容器，避免只报错却留下半成品环境。

这个实现适合本机和单机部署：管理服务直接操作 Docker，也直接承担到期回收。进入 Kubernetes 后，创建与清理会由管理服务和集群控制器共同完成。

Kubernetes 创建流程

管理服务与控制器

前面的 Docker 后端由管理服务直接创建和清理容器。使用 Kubernetes 时，管理服务会把镜像、资源限制和到期时间等要求写成一份资源记录，提交给集群。集群中的控制器读取这份记录，创建或分配 Pod，并持续更新运行状态；沙箱到期后，也由控制器发起回收。管理服务负责提交沙箱需求，控制器负责创建环境并管理后续变化。 需求保存在集群中，管理服务重启后，控制器仍能继续处理。

当前有两种 Kubernetes 容器工作负载实现，由 kubernetes.workload_provider 选择：

配置值 管理服务创建的资源 配套控制器
batchsandbox BatchSandbox OpenSandbox 仓库中的控制器
agent-sandbox agents.x-k8s.io 下的 Sandbox kubernetes-sigs/agent-sandbox 项目的控制器

两者在管理服务里都实现 WorkloadProvider 接口，负责资源的构造、提交、读取和删除。接口与注册代码分别位于 server/opensandbox_server/services/k8s/workload_provider.py 和 provider_factory.py。当前注册顺序下，不指定提供方时使用 batchsandbox。

接下来先沿 BatchSandbox 阅读，因为它完整展示了 OpenSandbox 自己的控制器和预热池设计。

CRD 与控制器

Kubernetes 自带 Pod、Deployment 等资源，但并没有内置 OpenSandbox 的沙箱类型。要让集群保存和管理沙箱需求，项目需要先通过 CRD（CustomResourceDefinition，自定义资源定义）向 Kubernetes 注册一种新资源。

CRD 定义资源的类型，创建请求提交的则是这个类型的一个实例。 例如，BatchSandbox 的 CRD 定义了它有哪些字段、字段是什么类型；管理服务为订单任务创建的某个 BatchSandbox，则保存这一次任务的镜像、资源和到期时间。注册后，这些实例也可以通过 Kubernetes API 或 kubectl 创建、查询和修改。

和常见的 Kubernetes 资源一样，一个 BatchSandbox 实例主要有以下几部分：

字段 作用 在沙箱中的例子
apiVersion、kind 标明资源属于哪个 API、是什么类型 sandbox.opensandbox.io/v1alpha1、BatchSandbox
metadata 标明资源的身份和附加信息 名称、命名空间、标签
spec 描述希望得到什么环境 Pod 模板、副本数、到期时间
status 记录控制器观察到的实际情况 已有多少 Pod、多少已经就绪

不过，注册 CRD 只是让 Kubernetes 能够识别和保存这种资源。要根据其中的要求创建沙箱，还需要配套的控制器。控制器持续比较 spec 中的要求与集群现状，执行必要的操作，再把结果更新到 status 中：

这就是 Kubernetes 常见的控制循环。资源变化会触发控制器重新检查，同一份需求也可能处理多次。因此，控制器每次都要结合当前状态决定下一步，已经创建好的 Pod 无需再创建一遍。

这里可以进一步分清 controller 和 Operator。Controller（控制器）是持续检查资源、执行调整逻辑的程序。 Kubernetes 自带的控制器会根据 Deployment 等资源管理应用副本；OpenSandbox 编写的 BatchSandbox 控制器，则根据沙箱资源创建 Pod、更新状态和处理到期回收。它们都采用前面介绍的控制循环。

Operator 是用自定义资源和控制器自动管理某类应用的一种方式。 以沙箱为例，原本需要管理员判断何时创建环境、补充预热容量、保存快照和释放资源。把这些管理规则写进控制器，让它根据资源中的要求持续执行，就构成了沙箱 Operator。

因此，Operator 的核心实现就是控制器，名称强调的是它具备某类应用的管理能力。一个 Operator 可以只有一个控制器，也可以由多个控制器协作；控制器数量并不是判断它是不是 Operator 的依据。

需要注意，CRD 和 Controller 是分开的。这是理解 Kubernetes Operator 的关键。

  • CRD：告诉 kube-apiserver，集群中新增了一种叫 BatchSandbox 的资源类型，以及它的数据结构和校验规则。
  • Controller：告诉自己的程序，需要监听 BatchSandbox，并根据它的期望状态执行操作。

一句话总结：CRD 负责定义资源，kube-apiserver 负责存储和提供 API，Controller 通过 Watch 主动监听资源，并通过 Reconcile 实现自动化管理。

在 OpenSandbox 中，这些职责由同一个控制程序中的多个控制器承担：BatchSandbox 控制器管理沙箱，Pool 控制器管理预热池，SandboxSnapshot 控制器管理快照。它们在 kubernetes/cmd/controller/main.go 中一起启动，共同完成这套沙箱 Operator 的工作。

BatchSandbox 采用的正是这套机制。Go 类型定义位于 kubernetes/apis/sandbox/v1alpha1/batchsandbox_types.go，生成的 CRD 清单位于 kubernetes/config/crd/bases/sandbox.opensandbox.io_batchsandboxes.yaml；控制器则基于 controller-runtime 实现，在 kubernetes/internal/controller/batchsandbox_controller.go 中监听 BatchSandbox 及相关 Pod 的变化。

有了这层背景，再看管理服务提交的 BatchSandbox，就可以把它理解为交给控制器处理的一份具体沙箱需求。

Kubernetes 预热池

提前准备

上面的流程适合按需创建，但每次都要等待 Pod 调度和容器启动。如果任务只运行几秒，环境准备就可能占去相当一部分时间。

预热池把 Pod 创建提前完成。部署者先定义一个 Pool，其中的模板决定 Pod 使用什么镜像、拥有多少资源，以及如何运行任务执行器。PoolReconciler 维护这些 Pod，请求到来时再分配。

Pool 的类型定义位于 kubernetes/apis/sandbox/v1alpha1/pool_types.go，容量配置主要包含两组边界：

字段 含义
bufferMin、bufferMax 希望保留的空闲预热 Pod 数量范围
poolMin、poolMax 整个池的 Pod 总数量范围，包含已分配的 Pod

空闲 Pod 被分走后，控制器会结合总量上限和扩缩容策略补充容量。空闲 Pod 超过保留范围时，也可以缩减数量。预热由此减少任务等待，同时占用一部分提前准备的计算资源。

分配工作由 Pool 控制器完成。kubernetes/internal/controller/allocator.go 先找到可以分配的 Pod，再计算每个 BatchSandbox 缺少多少个执行单元。当前默认算法位于 controller/algorithm/packed.go，按输入请求的顺序为它们分配可用 Pod。

对单个订单任务，可以先理解成：从池中找到一个就绪且未被占用的 Pod，记到这个 BatchSandbox 名下。分配完成后，BatchSandbox 控制器便能找到它，继续安排启动任务。

归还与补充

沙箱使用结束、需要归还 Pod 时，还要处理上一次任务留下的进程、文件和环境修改。只有明确这些内容怎样清理，池才能决定这个 Pod 何时可以再次分配。

Pool 通过回收策略决定如何处理归还的 Pod：

  • Delete：删除 Pod，再按容量要求补充环境。这是默认策略。
  • Restart：通过回收逻辑重启 Pod 中的容器。
  • Noop：不执行回收操作，保留原有环境。

这些策略的实现位于 kubernetes/internal/controller/recycle/。

这三种方式的清理范围不同。尤其是 Noop，不能据此认为环境已经恢复成最初状态；卷中的数据是否保留，也取决于卷本身的生命周期。

因此，预热池并不意味着同一个 Pod 要反复交给不同任务。默认策略可以在分配前提前建好 Pod，在归还后删除，再准备新的 Pod。它节省的是请求到来时的等待，环境是否原地复用则由回收策略决定。

生命周期管理

状态与失败

普通 Pod 和预热池两条路径最终都需要回答：这个沙箱现在能否使用？

BatchSandbox 控制器会统计已有 Pod、已分配 Pod 和就绪 Pod 的数量，并记录启动任务的运行、失败等情况。管理服务再通过 BatchSandboxProvider.get_status() 转换为应用看到的状态。

池里的 Pod 可能在分配前就已经就绪，因此仅看 Pod Ready 还不够。如果 task-executor 启动本次沙箱失败，Pod 仍在运行，沙箱却不能正常使用。当前状态转换逻辑会检查 taskFailed，将这类失败报告出来。这里的 taskFailed 记录的是 task-executor 管理的任务失败，例如启动脚本出错，导致沙箱没有正常启动。沙箱可用后，应用通过 commands.run() 运行的脚本由 execd 管理；脚本报错会返回到这次命令的执行结果中，不会直接计入 taskFailed。

普通 BatchSandbox 的 Pod 模板默认使用 restartPolicy: Never，部署模板可以显式调整。这个默认值符合沙箱任务的特点：容器重建可能丢失可写层和进程状态，程序重新启动并不代表原来的任务能够接着执行。

到期回收

客户端可能异常退出，所以环境不能只等应用主动删除。前面保存的 spec.expireTime 在这里发挥作用：BatchSandbox 控制器每次处理资源时都会检查到期时间，到期后发起删除。

续期的实现也很直接。server/opensandbox_server/services/k8s/batchsandbox_provider.py 中的 update_expiration() 修改同一个字段：

新的时间保存在集群里，后续检查会按新值安排回收。管理服务重启后，控制器仍可以读取它；控制器自身停机时，清理可能延后，但恢复后仍能判断哪些沙箱已经到期。

对比 Docker，这个差别就清楚了：Docker 的清理由管理服务中的定时器发起，BatchSandbox 的清理由集群控制器发起。回收职责跟着底层资源的管理方式走。

删除顺序

普通创建的 Pod 通过 ownerReferences 关联 BatchSandbox，删除资源时 Kubernetes 能够据此清理所属 Pod。预热池中的 Pod 属于 Pool，还需要先停掉本次任务，再交回池处理。

为保证清理顺序，控制器使用 finalizer。它是 Kubernetes 资源上的一种删除标记：资源收到删除请求后，先进入删除流程，等负责清理的控制器完成工作并移除标记，资源才最终消失。

管理服务自动创建的 PVC 也会尽可能关联到沙箱资源，方便沙箱到期时由 Kubernetes 回收。这里的 PVC 是申请持久化存储的资源；应用自备存储与管理服务代建的存储有不同的归属，不能把删除沙箱理解为删除所有挂载的数据。

暂停与恢复

Docker 暂停

如果任务需要等待较长时间，应用可能希望暂停环境，稍后继续。不过，不同运行时的暂停方式有明显区别。

Docker 后端调用容器的 pause() 和 unpause()：暂停原容器中的进程，恢复时继续运行。容器仍然存在，进程内存也仍然占用，适合暂时停止执行。

Docker 另有快照操作，会将容器文件系统提交为镜像，实现在 server/opensandbox_server/services/docker/snapshot_runtime.py。暂停原容器和保存文件系统镜像是两种操作，使用时需要分别理解。

Kubernetes 文件系统快照

BatchSandbox 暂停沙箱时，会删除承载它的 Pod，以释放计算资源。但删除 Pod 也会丢失容器可写层中的文件改动。因此，常规暂停流程会先把容器文件系统保存成镜像，确认保存成功后再释放 Pod；恢复时，用这个镜像重新创建环境。

管理服务先将 spec.pause 改为 true。kubernetes/internal/controller/batchsandbox_pause_resume.go 观察到这个请求后，创建一个内部 SandboxSnapshot 资源，由快照控制器保存容器文件系统。

这里先保存、后释放的顺序很重要。只有快照成功，后续恢复才有可用的环境；快照失败时，不能把源 Pod 当作已经可以丢弃的资源。进入 Paused 后，Pod 的实际删除仍可能需要一点时间。

环境恢复

恢复时，管理服务将 spec.pause 改为 false。控制器读取上次快照中的镜像引用，替换 Pod 模板里的镜像，再通过普通创建流程启动新 Pod。BatchSandbox 和沙箱 ID 保持不变，承载它的 Pod 可以变化。

原本来自预热池的沙箱也需要从自己的快照恢复。暂停流程会保存具体的 Pod 模板并解除池引用，恢复时按这份模板重建环境。

普通文件系统快照保存的是文件，正在运行的进程和 Python 内存变量不会因此恢复。 例如，已安装到容器文件系统里的依赖和写入其中的脚本可以随镜像保留；一个 Python 进程里尚未写入文件的计算结果则不在这种快照里。挂载卷中的数据仍由相应存储负责。

当前这条暂停恢复路径只支持 replicas: 1。仓库还包含专门的 QEMU 状态保存路径，其保存内容与普通容器文件系统快照不同。阅读或使用暂停功能时，需要确认实际采用的快照方式。

其他运行时接入

agent-sandbox

前面的 Kubernetes 实现使用 OpenSandbox 自己的 BatchSandbox 控制器。有些集群已经使用 kubernetes-sigs/agent-sandbox，OpenSandbox 也提供了对应接入。

配置 kubernetes.workload_provider = "agent-sandbox" 后，管理服务使用 AgentSandboxProvider，代码位于 server/opensandbox_server/services/k8s/agent_sandbox_provider.py。它构造的资源类型是 agents.x-k8s.io/v1beta1 下的 Sandbox。

应用请求仍然描述镜像、资源和存活时间，但写入集群时换成另一组字段：

沙箱需求 agent-sandbox 资源中的表达
用户容器配置 spec.podTemplate
到期时间 spec.shutdownTime
暂停 将 spec.operatingMode 改为 Suspended
恢复 将 spec.operatingMode 改为 Running

execd 的安装继续复用初始化容器和共享卷的构造逻辑。资源提交后，后续处理由 agent-sandbox 自己的控制器完成，OpenSandbox 读取它的状态并转换成沙箱状态。

因此，WorkloadProvider 统一的是管理服务怎样操作一种工作负载，具体的暂停和回收由配套控制器实现。BatchSandbox 的预热池分配、文件系统快照等流程，不能直接套用到这个提供方。

Fast Sandbox

容器之外，OpenSandbox 还可以接入独立项目 opensandbox-group/fast-sandbox，以 Firecracker 轻量虚拟机承载沙箱。

这里分工可以先看成两层：OpenSandbox 保留应用使用的沙箱 API，Fast Sandbox 平台负责准备模板和运行虚拟机。对应的 FastSandboxService 位于 server/opensandbox_server/services/fast_sandbox/。

它在 runtime.type = "kubernetes" 下由 CompositeSandboxService 分派请求。创建时指定 templateId，就进入这条路径；恢复 Fast Sandbox 生成的快照时也交给它。已有沙箱的后续操作，则通过 ID 的 fsb- 前缀识别。

模板已经准备好虚拟机使用的系统、依赖和 execd。平台再提前运行能够承载虚拟机的 Pod，一个这样的 Pod 可以提供多个虚拟机沙箱的容量：

管理服务把创建请求转换后，通过 gRPC 提交给平台的 FastPath 控制服务。平台利用已经准备好的容量创建沙箱，省去为每个新沙箱单独创建 Pod 的步骤。

FastSandboxService.create_sandbox() 会让创建调用等待一段配置的时间。如果平台已经保存创建需求，但环境尚未准备好，也可能返回 Pending，随后继续准备。它与前面 Kubernetes 容器后端等待 Running 或 Allocated 的行为有所不同，客户端仍需要确认环境可用。

Fast Sandbox 的暂停恢复由平台保存虚拟机检查点完成，可以包含文件系统、虚拟机状态和内存。OpenSandbox 负责提交操作并读取进度。平台内部的虚拟机运行逻辑位于独立项目中，本仓库主要实现对接代码；这也与 BatchSandbox 通过容器文件系统镜像恢复的方式不同。

底层隔离

Docker 和 Kubernetes 后端还可以结合不同的容器隔离机制。Docker 路径将配置的运行时传给 Docker Engine，Kubernetes 路径则可以为 Pod 写入 runtimeClassName，由节点侧选择相应的实现。

相关配置解析位于 server/opensandbox_server/services/runtime_resolver.py。例如，gVisor、Kata 等运行时会改变容器的隔离方式，但沙箱创建仍然沿 Docker 或 Kubernetes 的流程完成。

把这两层区分开，就能理解配置的作用：选择 Docker 或 Kubernetes，决定由谁管理环境；选择具体的容器运行时或虚拟机平台，决定环境底层怎样运行和隔离。

创建与回收全流程

回到最初的 Python 任务，几条运行路径可以放在一起比较：

小结

OpenSandbox 的运行时把“申请一个环境”落实为具体资源。Docker 后端直接管理容器；Kubernetes 后端先保存沙箱需求，再由控制器创建或分配 Pod。BatchSandbox 描述一次沙箱所需的环境，Pool 维护提前准备的容量，task-executor 负责在分配后启动沙箱，execd 随后接收应用的执行请求。

理解 Kubernetes 实现，可以沿着这条顺序阅读：请求怎样变成资源、资源怎样变成 Pod、Pod 怎样启动本次任务，以及任务结束后怎样释放环境。暂停恢复则进一步说明，同一个 API 在不同运行时下可能采用不同机制，需要结合实际保存的文件、进程和内存状态理解它的行为。

这些实现共同保留了沙箱这一层使用方式，也各自遵循底层平台的管理机制。应用可以围绕任务组织操作，环境的创建、等待和清理由运行时及其配套组件完成。
