AX 学习：核心功能与整体架构

发表于 2026-11-26 分类于 Go

上一篇介绍了 AX 的基础用法：创建任务、准备工作区、调用模型，以及暂停和恢复任务。这一篇从整体上分析 AX 的核心功能和架构，看看这些操作背后的组件如何配合。

下面先介绍 Task、Workspace、Gateway 和 Model 的职责，再梳理客户端、控制面和执行环境的关系，最后沿着一次任务的执行过程理解具体实现。本文依据源码 0bbe4f6 介绍当前实现。

功能范围

AX 的核心能力围绕任务执行展开：

  • 执行环境：指定镜像和计算资源，在独立沙箱中启动任务程序。
  • 工作区准备：准备代码、文件和依赖，供任务运行时使用。
  • 网络访问：限制任务能够访问的服务，并为请求注入凭据。
  • 生命周期管理：创建、启动、暂停、恢复和删除任务，查询运行状态。

AX 用资源配置描述这些需求，再由控制面和执行组件完成相应操作。下面先看资源的职责，再看它们如何转化为运行中的任务。

核心资源

Task

Task 是 AX 管理执行的基本单位。它描述任务使用的计算配置、启动命令、环境变量，以及需要引用的工作区和网络规则。

其中，spec.profile 指定镜像与 CPU、内存限制，spec.commands 指定实际运行的程序。最小任务可以只运行一条 shell 命令；复杂任务则可以启动 Claude Code、Codex 等智能体 CLI。

Task 提供程序运行所需的条件，程序本身实现具体逻辑。使用编程智能体时，规划、模型调用和工具调用由智能体完成，AX 管理它的执行环境。

任务镜像必须通过 digest 固定内容，例如 image@sha256:...。环境快照与具体镜像相关，固定镜像内容才能让后续恢复使用一致的基础环境。

Workspace

Task 解决了运行什么程序的问题，接下来需要准备程序要读取的内容。

Workspace 用于声明工作区的初始化内容，包括 Git 仓库、内联文件和初始化命令。默认工作目录是 /workspace，Task 通过 spec.workspace 引用它。

Workspace 将初始化内容分成几个字段：setup.git 声明需要克隆的仓库，setup.files 声明需要创建的文件，setup.commands 声明需要执行的初始化命令。它们负责准备工作环境，Task.spec.commands 则在环境就绪后启动实际任务。

更进一步，AX 会把准备好的环境保存为快照，供后续任务复用。多个任务引用同一个 Workspace，相当于从同一份准备结果开始工作，各自的修改仍保存在自己的执行环境中。

Workspace 可以通过 profile 为任务统一配置镜像和计算资源。Task 是否使用这份配置，取决于它有没有设置自己的 profile：

  • 没有设置：使用 Workspace 的 profile。
  • 已经设置：完整使用 Task 自己的 profile。其中未填写的资源限制采用系统默认值，不会从 Workspace 补齐。

这部分逻辑由 EffectiveProfile 实现。

Gateway

任务运行时可能需要访问模型服务、代码仓库或其他 API。Gateway 用于配置这些外部访问的范围，以及请求所需的认证凭据。

Gateway 描述允许任务访问的外部主机和端口，也可以为 HTTPS 请求配置凭据注入。Task 通过 spec.gateway 引用它；没有绑定 Gateway 的任务默认没有外部网络访问权限。

Gateway 保存策略，Substrate 的出站网关执行策略。启用 HTTPS 凭据注入后，任务发送占位认证头，网关读取授权的 Secret 并替换请求头，再转发给目标服务：

任务先发送一个占位认证头，出站网关再根据策略读取授权的 Secret，将占位值替换为真实凭据。这样，任务可以完成认证请求，而真实 token 无需写入 Task 清单或任务环境变量。

这些规则在绑定时复制到任务对应的执行实例。修改 Gateway 后，已经存在的任务仍使用原有规则，需要创建新的任务来使用调整后的策略。

Model

Model 将模型名称、提供商、生成参数和凭据引用保存为一份可命名的配置，供接入这套配置的模型调用代码读取。

但在当前版本中，Model 尚未接入 Task 的执行流程。创建一个 Model，可以通过 AX API 保存、查询和更新它，却不会改变任务中 Claude Code、Codex 或其他程序使用的模型。

源码中的 internal/model 客户端 已具备从存储中读取 Model 配置并发起模型请求的能力。不过，当前仓库中只有测试调用这个客户端，AX Server 和 runner 尚未使用它执行任务。因此，Model 目前主要完成了配置管理和客户端基础，实际任务仍需自行配置模型访问。

资源分组

四种资源都属于某个 atespace，默认名称为 default。Task 引用的 Workspace 和 Gateway 需要与它位于同一个 atespace。

Atespace 用于组织任务及其关联资源；Kubernetes 命名空间则用于部署 AX Server、数据库等基础组件，二者各有用途。

整体架构

资源描述了期望的执行条件，组件负责把这些条件变成运行中的任务。AX 的主要组件可以沿着控制请求和实际执行两条路径来看。

客户端

ax 读取清单，调用 AX 的 gRPC API。apply、get、describe、suspend、resume 和 delete 都是这套 API 的命令行入口。

Kubernetes context 是保存在 kubeconfig 中的一组连接配置，关联了要访问的集群、访问身份和默认命名空间。切换 context，就是选择这次命令使用哪组配置，常用于在本地、测试和生产集群之间切换。ax 会根据选中的 context 连接目标集群，找到其中的 ax-server，并在需要时建立端口转发。因此，切换 context 后，同一套 AX 命令就可以操作另一个环境。仓库也提供公开的 Go client，供其他程序使用相同的连接方式。

ax ssh 则用于进入任务执行命令或读取文件。它通过 Substrate 的路由服务访问沙箱内的 guest 服务，任务需要设置 spec.debug: true 才会开放这项能力。

AX 控制面

ax-server 负责接收 API 请求、校验资源、读写配置，并协调 Substrate 上的执行资源。它内部的 TaskManager 管理任务生命周期，WorkspaceManager 管理工作区初始化与快照。

AX 的资源虽然使用 Kubernetes 风格的清单，但没有作为 CRD 存进 etcd。按照 DESIGN.md 的设计，大量短生命周期任务会给 Kubernetes 的对象存储和控制面带来压力，因此 AX 将自己的资源保存在 PostgreSQL，通过 Substrate API 直接管理执行环境。

用户执行 ax resume 时，ax-server 收到请求后会调用 TaskManager，由它请求 Substrate 启动沙箱，再向沙箱内的 runner 下发任务。

Substrate 运行层

Agent Substrate 负责把任务安排到执行资源上，并管理沙箱的创建、暂停和恢复。要理解这一层，可以先看任务程序实际运行在哪里：

最外层是 Kubernetes 集群。 AX Server、数据库、Substrate 控制面和 Worker Pod 都部署在这里。Kubernetes 负责运行这些基础组件。

Worker Pod 提供任务的执行资源。 每个 Pod 中运行 worker 进程，由它创建和管理任务沙箱。WorkerPool 管理一组 Worker Pod；任务需要启动时，Substrate 从中选择资源足够、运行时匹配的 worker。

沙箱是任务程序所在的隔离环境。 一个 worker 可以承载多个沙箱，每个沙箱有自己的进程空间、文件系统视图和网络环境。沙箱内先启动 ax-runner，再由它启动具体程序。CPU、内存限制和网络规则作用于任务的执行环境。

本地部署使用 gVisor 创建这层隔离。它在任务程序与宿主机内核之间处理系统调用，减少任务程序直接接触宿主机内核的机会。图中的 gVisor 表示沙箱采用的隔离技术。

Substrate 用 actor 表示一个受管理的任务执行实例，记录它的身份、状态和运行位置。AX 为 Task 创建对应的 actor，actor 启动后在选定的 worker 上运行沙箱。ActorTemplate 则保存镜像、资源限制和挂载等运行配置，供多个 actor 复用。

沙箱内的 runner

沙箱启动后，还需要有人把配置变成进程。ax-runner 就是这一层的入口程序，负责准备工作目录、启动命令、转发停止信号，并提供就绪探针和元数据接口。

如果任务只给出了 goal 而没有显式命令，默认 runner 还支持调用镜像中的 ax-launcher。launcher 是镜像提供的启动程序，负责读取目标、配置和 MCP 信息并启动智能体。因此，使用自然语言目标时，也需要镜像具备相应的启动实现。

一次任务的执行

一次任务从资源提交到程序运行，会依次经过环境准备、资源创建和启动执行。沿着这个过程，可以看到各组件如何配合。

环境准备

任务引用 Workspace 时，需要先完成工作区准备。对于声明了初始化内容或计算配置的 Workspace，控制面会准备可供后续任务使用的环境快照。

WorkspaceManager 会创建一个临时 setup actor，在其中运行工作区初始化，等待准备完成后保存快照并创建标签。后续符合条件的任务，就可以从这份准备结果启动。临时 actor 完成工作后会被清理，快照标签用于后续复用。

这个流程位于 buildSnapshotWithSetupActor。文件、仓库和命令的具体准备工作由 SetupWorkspace 完成。

Workspace 通过 SetupComplete 和 SnapshotReady 两个状态条件，分别表示初始化已经完成、环境快照已经就绪。后续任务复用快照，可以减少重复准备文件和依赖的工作。

工作区初始化和任务执行还可以使用不同的 Gateway。例如，初始化需要下载依赖，正式任务只需要访问模型服务，就可以分别配置 Workspace.spec.setup.gateway 和 Task.spec.gateway。初始化阶段的访问权限不会自动传给任务。

资源创建

Workspace 和 Gateway 准备好后，CLI 提交 Task。服务端先校验引用的资源、计算配置等条件，再保存任务，并准备对应的 Substrate 资源。

启动与执行

执行恢复操作后，TaskManager.Resume 请求 Substrate 激活 actor。Substrate 安排运行位置并启动沙箱，AX 再通过路由服务，把 Task 和 Workspace 推送给 runner。

任务配置在这里采用推送方式，是因为 actor 模板可以被多个任务复用。模板描述共同的运行条件，具体任务内容在实例启动后交给 runner。

随后，runner 确认工作区就绪，再启动 Task 指定的程序。程序读取输入并执行任务；需要访问外部服务时，流量经出站网关按 Gateway 规则处理。

状态与持久化

状态的来源

任务配置保存在 AX 数据库，任务是否正在运行则由 Substrate 掌握。如果两边各自长期保存一份运行状态，就容易在暂停、故障或重新调度后出现不一致。

AX 因此把两类信息分开处理：

  • PostgreSQL 保存资源配置、元数据，以及工作区准备结果、资源创建失败等 AX 自己管理的信息。
  • Substrate 提供 actor 的当前状态、身份等执行信息。

Task 的 Running 表示沙箱正在运行。runner 在任务命令退出后仍会继续提供服务，因此，沙箱状态和程序是否完成需要分别判断。当前控制面不会自动把普通命令的退出码转成业务完成状态，任务结果需要通过程序输出或结果文件确认。

并发操作

状态分开保存之后，还需要防止多个请求同时修改同一个任务。例如，一个请求正在恢复任务，另一个请求又要删除它，两者必须协调。

AX 使用按资源区分的分布式锁，锁的租约保存在 PostgreSQL。不同任务可以分别操作，同一资源上的冲突操作则通过锁协调。

Workspace 的快照构建也采用锁：多个任务同时需要同一份尚未生成的快照时，由一个请求完成准备，其余请求等待并复用结果。这样可以减少重复创建 setup actor 的工作。

暂停与恢复

暂停任务时，Substrate 保存需要持久化的执行环境并释放运行资源。恢复时，再据此建立执行环境。

对于显式配置了 commands 的任务，恢复后会保留持久化的文件，并重新启动命令。程序需要将进度写入持久文件，在重新启动时读取这些记录，决定继续执行哪些工作。

AX 管理的默认 profile 快照还会保留容器文件系统状态，以支持 Workspace 初始化时安装的依赖。相关设置位于 DefaultProfileSnapshotFidelity。文件系统恢复和内存中的程序执行进度是不同层面的能力，任务程序仍需要根据自己的持久记录安排后续工作。

使用与扩展

本地与集群

AX 提供两种常见部署入口：

  • ax local start：准备本地 Kind、Substrate 和 AX 环境。
  • ax install：将 AX 安装到已经具备 Substrate 的 Kubernetes 集群。

两种环境使用相同的任务资源与 API。开发者可以先在本地验证镜像和清单，再通过 kubeconfig context 操作其他集群。ax studio 提供本地 Web 界面的启动入口，实际界面由独立的 AX Studio 程序提供。

跨集群复用配置时，可以使用 ax promote。它会处理 Task 及其引用的 Workspace、Gateway，并在目标环境创建任务。它复用的是资源配置，任务运行中产生的文件和 Gateway 引用的 Secret 需要另外准备；这项行为可在 promote 实现 中确认。

运行信息

组件分层之后，排查问题也需要先定位到具体一层：

  • 资源状态：ax describe 展示资源的条件与状态。
  • 业务执行：查看沙箱内的文件和程序输出。
  • 控制面：结合日志、指标与调用链，判断请求在哪个环节耗时或失败。

AX Server 使用 OpenTelemetry 接入日志上下文、指标、调用链和事件，并提供 Prometheus /metrics。使用 ax --trace 时，CLI 会输出 trace ID，相关 RPC 可以沿着 AX Server 继续关联到 Substrate。导出到外部后端的行为取决于部署中的遥测配置。

例如，任务无法恢复时，先看 Task 的条件信息，再判断是资源准备失败、worker 不可用，还是 runner 尚未就绪。相比仅看一个 Running 或 Suspended，这些信息更接近实际发生的问题。

能力边界

AX 已经具备任务生命周期、环境快照和受控网络访问等基础能力，部分面向智能体的配置仍在完善。

例如，当前服务端会拒绝 spec.retry，因为任务退出事件与自动重试流程尚未接通。Workspace 可以为 MCP 服务器生成配置供任务使用，但仍需要智能体或 launcher 读取；skills 的远程注册表下载也尚未实现，现有初始化代码主要负责准备目录。

这些区别关系到实际使用：资源中出现一个字段，说明接口已经描述了这类信息；是否能产生预期行为，还需要看对应的执行路径。本文讨论的能力以当前代码和已有实测结果为依据。

小结

AX 将智能体任务需要的运行条件组织为资源：Task 定义执行，Workspace 准备环境，Gateway 管理外部访问，Model 保存模型配置。控制面把这些配置交给 Substrate 管理的沙箱，再由 runner 启动实际程序。

沿着一次任务来看，就是先准备环境，再创建执行资源、启动命令、访问外部服务，最后保留文件并管理生命周期。理解这条路径，也就能看清 AX 的位置：它提供可复用的任务执行基础，让不同的脚本、模型客户端和编程智能体使用同一套环境管理方式。
