OpenSandbox 学习 01：快速入门

发表于 2026-11-16

AI Agent 正在把大模型的应用范围从对话扩展到实际工作。编程助手会修改代码、运行测试，数据分析助手会读取表格、执行 Python，浏览器助手会打开网页、填写表单。这些任务往往需要反复尝试：Agent 先执行一个操作，再根据结果决定下一步。要完成这样的工作，除了模型，还需要一套能运行程序、保存文件、返回执行结果的环境。

执行环境也带来了新的边界问题。Agent 可能生成有错误的代码，安装相互冲突的依赖，或者让一个进程长时间占用资源。如果多个任务和业务服务共用环境，一次试错就可能影响其他任务。沙箱的价值由此变得具体：为任务提供独立的工作环境，约束它能使用的资源和访问范围，并在任务结束后回收环境。隔离做到什么程度，则取决于底层运行时和部署配置。

AI 时代的 Sandbox

Docker 已经提供了容器、文件系统和资源限制，Kubernetes 则进一步解决了集群中的调度与容器管理。这些能力构成了沙箱的基础。不过，把它们接入 Agent 应用，还需要组织一套面向任务的使用流程。以数据分析为例，应用需要创建环境、等待环境可用、传入数据、执行脚本、收集输出、取回报告，最后清理资源。直接使用 Docker 或 Kubernetes 可以完成这些步骤，但应用需要自己处理相应的接口调用、状态检查和错误反馈。

OpenSandbox 把这些常见需求整理成一套沙箱服务：底层通过 Docker 或 Kubernetes 管理执行环境，上层通过统一的 API 和多语言 SDK 提供环境创建、命令执行、文件操作和生命周期管理。它的意义在于补齐容器基础设施与 Agent 应用之间的这一层，让开发者可以围绕“给任务一个环境，在里面完成工作”编写程序，减少每个应用重复维护执行环境的工作。

本文从本机 Docker 部署开始，用一个订单统计任务走完这条流程：把 CSV 和 Python 脚本上传到沙箱，计算不同品类的销售额，再把 JSON 报告带回本机。这个例子不依赖模型服务，便于先看清执行环境本身的工作方式；跑通之后，再沿着请求路径理解 SDK、管理服务和沙箱内部程序的分工。

项目与组件

核心架构

从整体上看，OpenSandbox 把 Agent 应用与底层执行环境连接起来。应用通过客户端接口发起操作，管理服务负责创建和回收沙箱，底层的 Docker 或 Kubernetes 提供运行环境；每个沙箱内部还有执行服务，负责接收命令、操作文件，并把结果返回给应用。

这里有两类职责。环境管理关心的是“任务在哪里运行”，任务执行关心的是“在环境里做什么”。创建一个沙箱和在沙箱中运行一段 Python，分别由不同的服务处理，整体关系如下：

一次任务会先经过环境管理这条路径：应用申请沙箱，管理服务调用运行时创建环境，再向客户端提供访问地址。环境可用后，命令和文件请求就发往沙箱的执行端点。本例采用直连方式，执行请求直接到达沙箱内部的服务；其他部署也可以通过网关路由这些请求。

这样的分工让管理服务专注于环境的创建、状态和回收，具体任务则在各自的沙箱内部执行。应用通过同一套客户端接口使用两类能力，无需自行拼接底层容器管理与任务执行的完整流程。

沙箱里既可以运行单个脚本，也可以运行完整的 Agent 程序。例如，将 Claude Code 启动在沙箱内，它就能在这个环境里调用模型、读写文件和执行命令；也可以让 Agent 运行在外部，仅把需要执行的任务交给沙箱。本文先用一个 Python 脚本演示沙箱的基本操作。

本文的组件

把这套架构放到本文的本机 Docker 部署中，各个位置就对应到下面这些具体组件。此时，一个沙箱就是一个 Docker 容器，客户端程序和管理服务都运行在宿主机上。

架构位置 组件 本文中的位置与职责
应用接入 Python SDK 由宿主机上的 main.py 调用，把创建、命令和文件操作转换为 API 请求
环境管理 管理服务（Lifecycle Server） 宿主机上的 FastAPI 服务，管理沙箱生命周期，调用运行时并返回访问地址
底层运行时 Docker 本机 Docker Engine，创建容器，提供进程、文件系统和资源限制
沙箱执行 execd 每个容器内部的 Go 程序，接收命令和文件请求，在沙箱内部完成操作

管理服务在项目中称为 Lifecycle Server，其中“生命周期”指一个环境从创建、使用到删除的过程。本文统一称它为“管理服务”。execd 则是沙箱中的执行服务：真正接到请求并运行 python /tmp/summarize.py 的就是它。认识了这两个角色，后面就可以沿着 “管理服务创建环境、execd 执行任务” 的路径阅读源码。

网络访问也有独立的组件配合这套架构：Ingress 负责外部请求进入沙箱时的路由，Egress 负责沙箱出站流量的策略控制。它们在部署到集群或需要限制网络访问时很有用。本文使用本机直连，也没有设置出站网络策略，因此不需要启动这两个组件。

请求背后的实现

到这里，已经有了一条完整的使用路径。接下来沿着刚才的几次调用看源码，就能理解这些能力分别放在哪一层，以及为什么普通 Python 镜像也能接收命令和文件请求。

管理服务

Sandbox.create() 首先调用管理 API。管理服务的创建路由位于 server/opensandbox_server/api/lifecycle.py，负责请求校验和规范化，然后把工作交给 sandbox_service.create_sandbox(request)，不会在路由函数里直接操作 Docker。

在本例的 Docker 部署中，管理服务启动容器后返回 Running 状态。此时容器里的 execd 可能还没准备好接收请求，因此 SDK 会继续做健康检查，确认它能够响应后，才返回可用的沙箱对象。

创建容器时，server/opensandbox_server/services/docker/container_ops.py 中的容器操作代码把 Linux 容器的入口设置为这个启动脚本。于是一个沙箱里既有用户镜像提供的 Python，也有 OpenSandbox 提供的 execd。启动脚本负责拉起执行服务和配置的入口命令，而订单统计脚本是在之后收到命令请求时才运行。

沙箱里的 execd 来自 execd_image 指定的镜像。修改 components/execd/ 下的源码后，需要重新构建镜像，并更新这项配置，修改才会在新建的沙箱中生效。

沙箱连接

容器启动后，宿主机上的 SDK 需要连接到容器里的 execd，才能上传文件、执行命令。execd 默认监听容器内的 44772 端口，本例由 Docker 将它映射到宿主机的一个端口，供 SDK 访问。

SDK 会向管理服务查询 execd 的访问地址，再用这个地址发送命令和文件请求。这里涉及两个地址：

  • 管理服务的 127.0.0.1:18080：用于创建、查询和删除沙箱。
  • execd 的访问地址：由管理服务返回，用于操作沙箱里的命令和文件。

对应的 RunCommand() 位于 components/execd/pkg/web/controller/command.go，负责校验请求、调用执行器，并把输出和完成或错误事件写回响应。前台命令使用 SSE，也就是在一个 HTTP 响应中持续发送事件；SDK 再把这些事件整理成 logs.stdout、logs.stderr、error 等字段。

这解释了示例为什么要分别看输出和执行状态。stdout 是程序打印的内容，stderr 是错误输出流，两者都不能独自代表最终成功与否。对于需要长时间展示进度的任务，SDK 还支持输出回调；本文任务很短，直接读取收集后的结果即可。

文件操作同样落在 execd。路由中的 /files/upload 和 /files/download 分别处理上传和下载。因此 write_files() 是把文件内容传到沙箱，read_file() 是把沙箱文件读回调用方；它们不会自动共享宿主机目录，也不会替应用永久保存产物。

执行环境的边界

理解了组件分工，也就更容易判断哪些事情需要应用自己安排。

  • 运行依赖由镜像提供。 本例只用标准库，所以普通 Python 镜像就够了。如果任务需要 pandas、浏览器或系统工具，应选择或构建相应镜像；OpenSandbox 不会根据脚本自动推断并补齐所有依赖。
  • 沙箱内的 Agent 也需要模型配置。 如果将 Claude Code 等 Agent 程序运行在沙箱里，需要为它配置模型服务地址、认证信息，并确保沙箱能够访问模型服务。OpenSandbox 提供运行环境，模型请求由沙箱里的 Agent 发起。
  • 持久化需要明确设计。 本例在删除前把报告带回本机。需要长期保存的数据，可以由应用写入对象存储，或在合适的场景使用卷挂载，不能依赖临时容器一直存在。
  • 网络权限需要单独设置。 本例使用 bridge 网络，没有配置 network_policy，因此没有启用 Egress 策略限制，不能把“运行在沙箱里”理解为“默认禁止联网”。

本例使用普通 Docker 容器，与宿主机共享内核。CPU、内存限制和容器文件系统提供了执行边界，但不等于虚拟机隔离。面向不可信代码的部署，还需要结合威胁模型选择安全运行时、网络策略和宿主机权限。

故障定位

发生问题时，可以按“管理服务 → 容器创建 → execd 端点 → 任务内容”的顺序缩小范围。每一层的成功，只说明这一层已经工作。

现象 优先检查的位置
/health 无法访问 管理服务终端日志、18080 是否被占用、配置路径是否正确
创建请求返回 401 两个终端是否加载同一份 .env，管理服务与 SDK 的密钥值是否一致
镜像拉取失败 宿主机能否手动 docker pull，Docker daemon 的代理和镜像仓库连接
创建沙箱失败 管理服务日志中的 Docker 错误、当前用户的 Docker 访问权限、资源是否充足
就绪检查超时 容器是否仍在运行、execd 日志、返回的宿主机映射端口是否可达
execution.error 有值 logs.stderr、脚本和依赖，随后检查执行错误及退出码
本机找不到报告 客户端是否完成 read_file() 和本地写入，是否在读取前删除了沙箱

示例结束后，在启动管理服务的终端按 Ctrl+C 即可停止管理服务。正常任务已经通过 destroy() 删除沙箱，本机报告仍保留在 ai_demo/opensandbox-quickstart/output/。如果客户端被强制结束而来不及清理，应检查遗留沙箱，不要把退出客户端或停止管理服务当成主动删除远端环境的替代操作。

小结

Agent 要完成实际任务，需要能够运行程序、操作文件并返回结果的工作环境。Docker 和 Kubernetes 提供了底层运行能力，OpenSandbox 则在此之上组织沙箱的创建、使用和回收，通过 API 与 SDK 将这些能力交给应用。

本文通过本机 Docker 部署和一份订单表，走完了“创建沙箱、上传输入、执行脚本、取回报告、清理环境”的完整流程。沿着这次调用阅读源码，可以看到清晰的组件分工：SDK 组织客户端操作，管理服务管理环境，Docker 创建并运行容器，execd 在容器内部处理命令和文件请求。环境管理与任务执行各自有独立的请求路径，连接关闭与远端沙箱删除也有不同的含义。理解这些关系后，部署、使用和排查问题就能对应到具体的一层。
