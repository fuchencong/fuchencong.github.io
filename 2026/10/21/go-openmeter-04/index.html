OpenMeter 学习 04：数据存储设计

发表于 2026-10-21 分类于 Go

本文介绍 OpenMeter 的数据存储设计，结合源码分析用量事件、客户订阅、额度余额、账单和账务记录等数据的保存方式，以及各个存储组件的作用与选型取舍。OpenMeter 使用 ClickHouse 保存和查询用量明细，使用 PostgreSQL 管理业务状态，通过 Kafka 传递使用事件和业务消息，并按配置使用 Redis 保存去重索引与查询进度。下文先介绍整体分工，再分别展开各类数据的存储结构与读写流程。

存储版图

数据的归属

不同数据的访问方式决定了存储需求。客户资料、套餐单价和订阅日期需要经常按实体读取，也需要协调修改；用量记录主要是持续追加，再按客户和时间范围汇总。前者关心“这次修改是否完整提交”，后者关心“大量记录能否高效写入和扫描”。

按数据的性质和用途，可以将存储分工归纳为下面几类：

数据类型 实际例子 主要存储 存储需求
用量明细 Token 消耗、请求次数、存储用量事件 ClickHouse 持续追加，按时间和业务维度批量聚合
业务配置与状态 计量规则、套餐价格、客户订阅 PostgreSQL 按实体读写，保证关联修改的完整性与一致性
计算检查点 额度余额快照 PostgreSQL 保存可复用的中间状态，减少重复计算
历史凭据 已出账明细、账务分录、通知载荷 PostgreSQL 保留当时的结果与依据，支持查询和追溯
异步消息 待处理的使用事件、订阅变更消息 Kafka，部分消息先写入 PostgreSQL outbox 连接处理阶段，支持缓冲、消费与重试
短期辅助状态 去重标记、查询进度 按配置使用内存或 Redis 快速读写，并通过容量限制或有效期控制保留范围

其中最容易混淆的是计量器和用量：计量器定义保存在 PostgreSQL，用量明细保存在 ClickHouse。 创建一个求和计量器，保存的是“怎样解释事件”的规则，并不等于在关系数据库中创建了一张用量表。

同样，Kafka 中的消息和 ClickHouse 中的行虽然可能描述同一次调用，职责也不同。前者用于把工作交给消费者，后者用于长期查询和计量。

两条数据路径

用量接入与订阅管理可以画成两条路径。下面省略观测设施和配置依赖，业务事件处理以相关功能启用为前提。

两条路径最终会相遇：费用计算需要读取订阅条款，也需要查询这段时间的实际用量。但它们并没有共享一笔覆盖 PostgreSQL、Kafka 和 ClickHouse 的事务。系统通过本地事务、消息重试、快照和明确的时间边界衔接各个阶段。

ClickHouse 的用量明细

ClickHouse 基础

用量记录不断增加后，数据库需要处理的往往不再是“找到某一条调用”，而是“汇总这个月所有客户的消耗，再按模型和地区分组”。这样的查询可能涉及数百万甚至更多记录，但最终只返回几十行结果。ClickHouse 就是面向这类分析任务的数据库。

ClickHouse 是一个开源的列式数据库，支持使用 SQL 对大量数据进行筛选、分组和聚合。这类工作通常称为在线分析处理（Online Analytical Processing，简称 OLAP）。这里的“在线”指可以直接执行查询并获取结果，不意味着数据写入后一定立即可见，也不意味着任何查询都能在固定时间内完成。

它的核心特点是按列组织数据。我们平时看到的表仍然有行和列，但底层存储方式不同。下面用三条使用记录说明这种区别，图中只是逻辑示意，不代表实际文件格式：

行式存储把同一条记录的字段组织在一起，适合按主键读取或修改完整记录。列式存储把同一列的数据组织在一起：计算 Token 总量时，主要读取 tokens 列；按模型统计时，再读取 model 列。表中即使还有请求参数、错误信息等其他列，也不必为了这次汇总全部读出。对于扫描很多行、只使用少数列的查询，这可以减少读取的数据量。

同一列的数据类型相同，取值也可能重复，因而更便于采用合适的编码与压缩方式。ClickHouse 还会成批处理数据，让一次计算作用于一组值，并利用多个 CPU 核心并行执行查询。这些能力共同服务于一个目标：高效地从大量明细中得到统计结果。

不过，列式存储只是基础。实际查询速度还取决于分区、排序、过滤条件和读取范围。如果一条查询必须扫描几年的数据，再解析每条记录中的复杂 JSON，工作量仍然很大。后面分析 OpenMeter 的表结构时，会具体讨论这些因素。

核心能力与场景

从使用者的角度看，ClickHouse 的主要能力包括：

  • 明细存储：持续接收事件、日志等记录，同时保留后续查询所需的字段。
  • 统计分析：通过 SQL 计算总量、平均值、去重数量、分位数等，并按时间、客户或业务维度分组。
  • 时间范围查询：配合分区和排序，从大量历史数据中筛选某段时间的记录。
  • 分析加速：支持物化视图等机制，按需要预先处理部分数据；具体项目是否使用，需要查看实现。

因此，它常见于日志分析、网站与应用行为分析、监控指标分析、广告效果统计，以及 OpenMeter 这样的用量计量系统。这些场景通常持续产生新记录，查询则关注一段时间内的趋势、分布或汇总值。

另一类工作是修改订单、维护订阅、扣减库存：每次操作涉及的记录可能很少，却要求多项修改完整提交，并正确处理并发。这类工作通常称为在线事务处理（Online Transaction Processing，简称 OLTP），也是 PostgreSQL 等关系数据库的常见用途。两类数据库的能力存在交集，但优化重点不同。ClickHouse 更适合以追加写入和批量分析为主的数据，频繁的逐行修改和复杂业务事务通常会交给其他存储处理。

在 OpenMeter 中，ClickHouse 负责保存使用事件，并根据计量规则查询这些事件。例如“客户本月用了多少 Token”“不同模型分别消耗多少”，都属于它擅长的分析任务。客户买了什么套餐、订阅何时到期、账单处于什么状态，则由 PostgreSQL 管理。下面先通过一组简单 SQL 熟悉它的用法，再看 OpenMeter 如何组织实际数据。

末尾的 toStartOfHour(time) 表示按小时起点参与存储排序。例如 08:15 和 08:40 都对应 08:00，但原来的事件行和 time 列仍然保留。存储排序不会把一个小时的事件合成一条汇总记录。

stored_at 上还有一个 minmax 索引，用于记录数据块的最小、最大值，让数据库在某些过滤条件下跳过整个块。它是辅助减少扫描的机制，实际效果取决于数据分布，初次阅读时不必先掌握其中的粒度参数。

这里还可以确认两个边界：建表语句没有设置自动过期删除规则，按月分区不意味着数据会按月自动清理；普通 MergeTree 也没有给业务事件 ID 提供唯一约束。去重由应用处理，后面的 Redis 部分会介绍。

这些查询得到的是使用数量。客户订阅条款、额度扣减和最终账单还需要其他模块结合规则处理，下面转向保存这些业务状态的 PostgreSQL。

PostgreSQL 的业务状态

实体与约束

如果说使用事件回答“发生过什么”，业务数据库就要回答“客户现在按什么规则使用和付费”。这里的修改往往跨越多个实体：创建订阅可能同时生成阶段、条目和权益；更新账单可能改变明细、汇总和状态。它们需要完整提交，也需要明确的关系与约束。

OpenMeter 通过 Ent 描述大部分持久化实体，schema 目录是理解数据结构的主要入口，生成代码目录提供查询与写入接口。运行时，数据库组装代码将 PostgreSQL 驱动、sql.DB 和 Ent client 连接起来。

许多业务实体复用公共字段：

  • id：通常由 ULID 生成，PostgreSQL 中使用 char(26)。
  • namespace：标识业务空间，作为大量查询和复合索引的条件。
  • created_at、updated_at、deleted_at：保存记录时间与删除可见性。
  • metadata、annotations：保存扩展信息或系统标记。

这些字段由 Ent mixin提供，不过不能因此推断所有表完全同构。例如 outbox 使用递增序列 ID，也没有沿用普通业务实体的软删除方式。

namespace 在这里是数据模型中的逻辑隔离，不等于每个租户拥有一个 PostgreSQL 数据库。相应地，查询和约束需要带上 namespace。以计量器为例，活跃定义的 key 受下面这个复合唯一索引约束：

关系字段与 JSONB

业务配置既有稳定结构，也有变化较多的部分。客户 ID、币种、阶段起点适合独立字段；阶梯价格、权益模板、折扣组合则更像一个内部结构完整的配置对象。OpenMeter 因此没有将全部业务对象塞进单个 JSON，也没有把每一种价格形态都拆成大量固定列。它使用关系字段保存身份、关联、状态和主要时间，再用 JSONB（Binary JSON）保存部分结构化配置。

商品目录本身也有关系结构。套餐 schema保存 key、version、币种、生效范围和结算方式，下接套餐阶段与费率卡；活跃版本通过 (namespace, key, version) 唯一索引区分。这个版本表达商品目录中的商业配置，与下面客户订阅的条目历史是两个层面。

订阅的时间结构

客户订阅也不是一行 plan_id 就能表达。套餐可以更新，客户可以中途升级、预约取消，也可能拥有单独协商的价格。历史上某段时间使用什么条款，需要从客户自己的订阅安排中读出来。

当前订阅模型主要由三层组成：

订阅保存客户、账期锚点、周期和结算方式；阶段组织商业安排；条目保存有效时间和费率卡内容，包括价格、折扣及权益模板等。商品目录是生成这些安排的来源，已经形成的客户条款则有自己的持久化表示。

阶段与条目的时间结构还有一处区别：阶段行主要保存起点，阶段结束需要根据下一个阶段或订阅结束推导；条目保存自己的生效区间，并可保存相对阶段起点的时间覆盖信息。订阅领域文档明确要求，不要把推导出的阶段结束误当成另一份独立事实。

这样保存，才能描述“先试用，后正式收费”以及“同一条目在不同时间采用不同条款”。它也解释了为什么订阅更新需要领域服务协调多个实体，而不是直接改一张表中的价格字段。

此外，更新可能删除并重新创建阶段、条目及其权益。物理行 ID 不一定是某条逻辑商业安排永远不变的身份。下游同步需要理解领域中的逻辑引用，不能只凭一行是否换了 ID 就认定客户购买了全新的商品。

事务与并发

关系数据库选型的另一个理由，来自多个进程同时修改同一份客户状态的场景。

例如两个任务同时尝试为同一客户创建待出账容器。即使每个任务内部都执行“先查，没有则创建”，它们仍可能在相同时间看到空结果。需要把并发控制放进事务，并让数据库约束成为最后一道保护。

OpenMeter 的计费锁实现维护客户锁记录，通过 Ent 的 ForUpdate() 在事务中锁定。同一客户的账单操作因此可以串行执行。与此同时，账单 schema还有一个部分唯一索引：

这些能力说明了 PostgreSQL 在项目里的角色：它不只是保存对象的地方，也承担局部原子性、关系约束和并发协调。至于事务提交之后怎样可靠地通知其他进程，还需要 Kafka 与 outbox 配合。

Kafka 的事件日志

使用事件

调用量增长时，接入速度和 ClickHouse 写入速度不一定始终一致。写入节点短暂变慢，不应该立即让所有事件生产者跟着堵塞；消费者也需要在重启后继续处理尚未完成的数据。Kafka 为这两个阶段提供消息日志和消费位置。接入侧负责发布，Sink 消费并批量写入，积压量反映两者的速度差。保留期内的消息还可以按消费位置重新读取，但 Kafka 的保留策略仍由实际 broker 和 topic 配置决定，不能把它当成永久档案。

重新读取是一项能力，也需要明确的消费位置操作。当前 Sink 将无有效 offset 时的重置策略固定为 latest；如果消费位置缺失或过期，它不会自动从最早保留消息开始补齐。正常重启后的继续消费，与主动回放历史，是不同的运行场景。

当前接入 topic 解析器根据 namespace 套用模板，默认模板是 om_%s_events。消息中保存序列化后的 CloudEvent，并通过 header 携带 namespace、接入时间和追踪信息。

领域事件

Kafka 的第二项工作，是传递订阅变更、账单变更、用量落库通知、权益值更新等消息。这些消息用于让不同业务模块继续工作。当前配置区分了 system events、ingest events、balance worker events 等 topic。它们与原始用量 topic 不同：原始事件描述一次使用，领域事件描述一次业务变化或后台处理结果。

同样重要的是，收到一个“用量已更新”的通知，不等于通知本身保存了完整业务状态。 Balance worker 仍需要查询用量并结合 PostgreSQL 中的权益和授予进行计算；Billing worker 也需要读取已提交的订阅安排。消费者各自使用自己的消费组推进，彼此完成时间可以不同。

接入日志、领域消息和关系数据库共同协作，但当前系统并不是把所有业务状态都通过重放 Kafka 历史重新构建。客户、订阅、账单等对象在 PostgreSQL 中有直接的持久化模型；Kafka 消息不能替代这些业务表的备份。

事务消息

订阅修改引出了一个经典的双写问题：如果 PostgreSQL 已经提交，而进程在发送 Kafka 消息前崩溃，计费模块就可能错过这次变化。反过来，如果先发消息再提交数据库，消费者也可能看见一条最终回滚的修改。

OpenMeter 对配置进入 outbox 的消息，先在同一笔 PostgreSQL 事务中写入待发送记录。当前应用组装只把 system-events topic 加入 OutboxTopics，其他 topic 仍可直接发布。因此，不能将所有 Kafka 消息都描述成具有事务 outbox 保护。

后台 worker 通过 FOR UPDATE SKIP LOCKED 领取某个来源事务的队列头，再按序列 ID 发送同一事务的消息。多个 worker 可以处理不同事务，而不需要业务请求等待 Kafka 网络调用。

这解决了“业务提交后消息记录丢失”的主要窗口，但仍有两项限制：

  • Kafka 已确认发送，而删除 outbox 的数据库事务未提交时，消息可能再次发送。消费者仍需容忍重复。
  • 达到最大尝试次数的记录会保留以供检查，但后续 drain 会跳过。有限重试不是无限期保证最终送达。

顺序保证也只作用于同一来源事务的发送过程；它不能扩展成不同事务、不同 topic 或不同 Kafka 分区之间的全局顺序。

Outbox 的领域说明明确指出，成功发送后记录会被硬删除。它是一张交付队列表，不是永久事件档案。这里的 PostgreSQL 和 Kafka 不是保存两份相同历史，而是先后承担“提交后待发送”和“消费者可读取”的责任。

Redis 的短期状态

去重索引

客户端上报事件后，可能因为网络超时而重新发送同一条记录。如果这些记录都参与统计，同一次使用就会被重复计量。OpenMeter 在处理事件时通过去重索引识别已经处理过的记录，Redis 是其中一种可选的索引存储。

这里必须区分两个使用位置：

  • 接入侧去重：包装 Collector，先检查并登记身份，再决定是否继续发送。
  • Sink 去重：先批量检查已有身份，成功写入用量后，再登记成功记录。

前者可以减少重复消息进入 Kafka，后者贴近最终存储。它们使用独立配置项，不能把“启用了某处去重”直接解释成整个链路拥有相同保证。

Redis 在这里也不只是提升速度的缓存。去重键丢失或过期，会改变后续重试是否被接纳；接入侧先登记再发送，还存在发送失败而身份已经登记的窗口。系统没有把 Redis 和 Kafka 的这两个操作包进同一事务。

这也是为什么短期去重不等于永久幂等：超过有效期再次上报相同事件，或者相关索引状态丢失，系统就可能重新接纳它。事件表自身又没有唯一约束，最终仍需结合生产者重试方式和业务身份设计理解重复风险。

查询进度

另一个 Redis 用途来自大范围查询。用户等待长查询时，希望知道它仍在执行，而不是只能盯着一个没有反馈的请求。

Progress manager将进度对象序列化为 JSON，使用 namespace、进度 ID 和可选前缀组织 key，再通过普通 Redis SET 保存。默认过期时间是五分钟；未启用时，依赖组装使用 noop 实现。

这类数据生命周期短、读写简单，并且需要跨 API 请求读取，适合使用带 TTL 的键值存储。它没有承担客户余额或账单状态的事实来源，丢失后也不能据此判断用量数据丢失。

由此可以看到，即使同样保存在 Redis，去重索引和查询进度的丢失后果也不同。分析存储可靠性时，需要先看数据用途，不能仅按组件名称把所有 Redis 数据都归入“随时可以丢弃的缓存”。

保留与演进

数据的保留期

采用多个存储之后，数据保留也变成了几套不同策略。

Kafka 的保留期决定还能回读多早的消息；Redis 的 TTL 决定短期辅助状态存活多久；ClickHouse 事件的保留范围决定还能重查多早的使用事实；PostgreSQL 中的软删除记录、账单和账务历史则有各自的业务含义。

当前事件表建表语句没有默认 TTL，不能凭月份分区推断系统已经自动清理旧事件。当前 outbox 则相反：成功交付后会删除记录。二者看似都保存“事件”，生命周期却不同。

还需要考虑数据之间的依赖。如果历史原始事件已经删除，而某项计算又需要从计量起点重算，仅保存若干余额快照未必足以满足要求。是否可以删除某段输入，需要结合查询需求、有效检查点和历史计费凭据一起决定，不能只看磁盘占用。

结构迁移

数据结构会随着产品模型变化。价格增加单位换算、账务增加来源维度、快照增加完整周期状态，都不仅仅是多写一个 Go 字段：旧数据和滚动升级中的旧进程仍然存在。

OpenMeter 的 PostgreSQL 结构由 Ent schema 描述，版本化 SQL 位于 migrations 目录。启动迁移器根据配置执行 migration，或等待独立迁移 job；仓库的 Makefile 还包含 schema、迁移差异和校验和检查。

ClickHouse 这条路径则在连接器启动时执行 CREATE TABLE IF NOT EXISTS。这个语句可以确保表存在，却不会自动将已经存在的旧表改成新的列定义。因此，阅读新版本源码看到新增列时，还需要核对对应升级步骤，而不能把建表函数当成完整的 schema 演进机制。

JSONB 同样需要迁移与兼容。前面提到的旧 usage 与新 usage_snapshot 并存，就是为了让升级过程中的读写双方逐步过渡。某个字段使用 JSON 存储，只是把内部结构交给编码和解码逻辑管理，并没有让历史结构问题消失。

存储取舍

用量明细与业务状态的访问需求不同，OpenMeter 因此分别围绕 ClickHouse 和 PostgreSQL 组织这两类数据。

ClickHouse 围绕追加明细和范围聚合组织数据。月份分区、按业务空间和使用主体排序、批量插入，服务于大量用量记录；JSON 载荷和查询时取值保留了计量定义的灵活性。它承担的成本是扫描与解析，以及由外部机制处理重复事件的需要。

PostgreSQL 围绕客户商业状态与历史凭据组织数据。关系字段、JSONB、唯一约束、事务和锁，让订阅、费用、账单和账务记录能够协调变化；必要快照让历史结果不依赖今天的配置。它承担的成本是更复杂的实体关系、并发控制和结构迁移。

Kafka 让接收速度与处理速度可以暂时不同，也让多个后台模块各自推进。它带来缓冲和重新读取的能力，同时把“什么时候已可查询、什么时候已完成计费”变成必须显式说明的边界。Redis 则补充跨实例的短期索引与进度状态，但它不能代替用量明细、商业状态或永久幂等记录。

这些组件的价值最终落在同一件具体事情上：客户的一次使用，可以持续进入系统；客户的商业条款，可以完整提交；收费结果和历史凭据，可以解释它们当时依据了什么。OpenMeter 的存储设计，就是围绕这几种不同的数据责任，把写入、计算和历史保存连接起来。

小结

OpenMeter 根据数据的访问方式安排存储：ClickHouse 保存用量明细，支持按时间和业务维度聚合；PostgreSQL 保存配置、订阅、账单和账务记录，提供事务与关系约束；Kafka 连接事件接收和后台处理；Redis 按需保存去重索引和查询进度。
