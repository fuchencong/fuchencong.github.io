OpenMeter 学习 01：快速入门

发表于 2026-10-14 分类于 Go

很多产品的价格与资源消耗有关：API 按调用次数收费，AI 产品按 Token 收费，CI 平台按构建分钟收费。真正麻烦的地方通常不在“加一”，而在于事件来源很多、需要按客户和时间窗口聚合，还要处理重试、重复上报、迟到事件以及后续的额度和账单。OpenMeter 把这部分工作拆成一条可观察的事件链路：应用发送使用事件，系统把事件可靠地写入消息队列，再由 worker 校验、去重和保存；查询接口从用量存储中按计量器计算结果。这样，业务代码只需要描述“发生了什么”，不用在每个服务里重复实现计数和聚合逻辑。

本文使用仓库中的 quickstart/ 目录完成一次真实部署，验证以下路径：

  • Docker Compose 启动 OpenMeter API、worker 和依赖服务；
  • 通过 CloudEvents 上报一次 API 请求；
  • 等待异步处理完成并查询 COUNT 计量器；
  • 验证相同 source 和 id 的重复事件不会被重复计量；
  • 验证 SUM 计量器和 groupBy 查询。

文中的命令都从仓库根目录下的 quickstart/ 执行，读者可以直接复制运行。这个 Compose 配置使用 latest 镜像和开发级依赖，适合学习和本地评估，不是生产拓扑。

OpenMeter 简介

OpenMeter 是面向 AI、API 和其他使用量产品的开源变现基础设施。它把产品中的请求、Token、计算时长等使用记录转换为可查询的实时用量，并在此基础上提供额度控制和使用量计费能力。项目采用 API-first 的设计，可以独立承担从原始事件到发票的完整链路，也可以只接入其中的计量、额度或计费部分。

一个使用量产品通常要同时解决几件事：准确记录每次使用，按客户、时间窗口和业务维度聚合，判断客户是否还有可用额度，最后根据价格生成账单。OpenMeter 将这些问题拆成相互衔接的核心能力：

  • 用量计量：接收符合 CloudEvents 规范的事件，通过计量器定义聚合次数、时长、Token 或其他数值。subject 标识使用者，groupBy 保存方法、路由、模型等维度；
  • 产品与定价：定义 feature、plan、addon、rate card 和 subscription，支持固定费用、周期费用、按量、分层和套餐等价格形式；
  • 额度与访问控制：根据客户的 entitlement、credit grant 和计量结果计算余额，供业务系统判断是否继续提供某项功能；
  • 使用量计费：把订阅和用量转换为 charge、invoice，推进账单计算、收集和支付相关的生命周期；
  • 开放集成：通过 REST API、JavaScript、Python 和 Go SDK 接入业务系统，并通过 webhook 或外部发票、支付和税务服务连接现有基础设施。

CloudEvents 规范

CloudEvents 是 CNCF 推动的一种事件描述规范，目的是让不同服务产生的事件拥有统一的外层格式。无论事件来自 API 网关、模型服务还是任务调度器，接收方都可以用相同的方式读取事件身份、类型和来源，而不必为每个生产者编写一套解析逻辑。

一个 OpenMeter 事件通常包含以下上下文字段：

  • specversion：CloudEvents 规范版本，示例使用 1.0；
  • id：事件在同一来源中的唯一标识，用于重试和去重；
  • source：产生事件的服务或系统；
  • type：事件类型，例如 request 或 prompt；
  • subject：事件归属的使用者，例如客户或工作区；
  • data：事件的业务数据，例如请求路由、执行时长或 Token 数量。

OpenMeter 当前通过 JSON 格式接收 CloudEvents，data 可以是任意合法的 JSON 对象。计量器使用 JsonPath 从 data 中取值，例如 $.duration_ms 表示读取 data.duration_ms。因此，CloudEvents 负责统一事件的外层结构，计量器负责解释业务数据，两者结合后，同一种事件格式就可以服务于计数、求和和维度分组等不同场景。

OpenMeter 负责用量和账单领域的核心状态，但不替代支付处理器、税务引擎或通用会计系统。它更像一层可组合的计费基础设施：产品可以先使用计量器和查询 API，之后再逐步加入 entitlement、订阅和 billing。本次入门先跑通最基础的事件计量链路，后面的组件和源码分析也会围绕这条链路展开。

运行组件

OpenMeter 把高吞吐的事件数据和需要事务一致性的业务状态放在不同的存储中。这是架构中最重要的分界：ClickHouse 负责事件和聚合查询，PostgreSQL 负责客户、计量器、产品目录、订阅、额度和账单状态。

组件 在链路中的职责 quickstart 中的服务
API server 接收事件、管理计量器、提供用量查询和管理 API openmeter
Kafka 把接收和处理解耦，承载使用事件及领域事件 kafka
Sink worker 消费使用事件，校验、去重、匹配计量器并写入 ClickHouse sink-worker
ClickHouse 保存原始用量并执行计量聚合查询 clickhouse
PostgreSQL 保存计量器和产品、客户、订阅、额度、账单等事务状态 postgres
Redis quickstart 中用于 sink 去重，也可保存查询进度 redis
Balance worker 依据使用量和 grant 重新计算 metered entitlement 余额 balance-worker
Billing worker 同步订阅、计算 charge 并推进 invoice 生命周期 billing-worker
Notification service 评估通知规则并记录待发送事件 notification-service
Jobs 执行迁移、订阅同步等定时维护任务 openmeter-jobs
Svix 提供 webhook 投递服务 svix

把这条运行链路按数据流拆开，可以分成几步：

  1. 业务服务或 SDK 先把 CloudEvents 发送给 API server
  2. API server 将事件写入 Kafka，同时从 PostgreSQL 读取和保存计量器、客户、订阅等业务状态
  3. Sink worker 消费 Kafka 中的使用事件，完成校验、去重和计量器匹配后，把原始事件写入 ClickHouse，去重键保存在 Redis 中
  4. 查询请求仍然由 API server 接收，再交给 ClickHouse 返回聚合后的用量
  5. Balance worker 和 Billing worker 也消费 Kafka 中的相关事件，分别负责额度计算和账单处理。

Kafka 的意义是让 API 不必同步等待 ClickHouse 写入。API 返回成功，表示事件已经交给 collector；之后 sink worker 才会消费和落库。因此，刚上报事件时立刻查询到空数组是正常的，客户端需要等待一小段时间再查询。

计量器配置

业务服务上报的是一条条原始事件，但产品真正关心的通常不是事件本身，而是 某个客户在一段时间内用了多少。例如，同样一条 API 请求事件，既可以计入请求次数，也可以计入执行时长；同样一条模型调用事件，还可以分别统计输入 Token 和输出 Token。若把这些计算逻辑分散到各个业务服务中，产品改一次计费口径，就要同时修改生产事件的代码和查询逻辑。

计量器（meter）就是 OpenMeter 对这种计算口径的声明。它把四件事写在一起：要匹配哪种事件、从事件数据中取什么值、使用哪种聚合方式，以及按哪些维度拆分结果。事件生产方只负责如实上报使用事实，计量器则负责把这些事实解释成“请求数”“请求时长”或“Token 用量”等指标。这样，同一份事件可以被多个计量器复用，计费规则变化时也可以优先调整配置和后续的价格模型。

在配置文件中，meters 是计量器列表，每个计量器通过 slug 定义稳定的查询名称。常见字段的关系如下：

  • eventType 决定计量器接收哪类事件，必须与 CloudEvent 的 type 对应；
  • aggregation 决定如何合并匹配到的事件，支持 COUNT、SUM、AVG、MIN、MAX、UNIQUE_COUNT 和 LATEST；
  • valueProperty 用 JsonPath 指向数值字段，COUNT 不需要它，其他需要数值的聚合通常都需要它；
  • groupBy 把事件中的字段映射为查询维度，例如按 HTTP 方法、路由或模型分别统计。

事件链路

现在沿源码把刚才的结果串起来。

API 与 Kafka

openmeter/ingest/kafkaingest/collector.go 的 Collector.Ingest 先根据 namespace 解析 Kafka topic，再序列化 CloudEvent 并发布消息。默认 topic 模板来自配置 om_%s_events，所以不同 namespace 的事件会进入不同 topic。这样既能让租户数据隔离，也能让 sink worker 按 namespace 刷新计量器。

Sink 与 ClickHouse

Sink worker 从 Kafka 消费消息，先放入 buffer；达到 minCommitCount 或等待时间后触发 flush。flush 阶段会依次完成：

  • 解析 Kafka 消息中的 CloudEvent 和 namespace；
  • 用 source + id 检查重复事件；
  • 从 meter cache 找出受影响的计量器；
  • 校验事件数据并把结果写入 ClickHouse；
  • 提交 Kafka offset，并发布 ingest notification。

计量与计费边界

到这里只使用了 meter 和 streaming 两个核心部分。它们回答的是“客户用了多少”。如果产品还要回答“客户现在能不能继续用”或“这次使用应收多少钱”，则会进入另外两条链路：

  • entitlement 将 feature、customer attribution 和 grant 联系起来，balance worker 在使用量变化后重新计算余额；
  • product catalog 和 subscription 描述产品、价格和客户订阅，billing worker 再把可计费工作转换为 charge 和 invoice；
  • ledger 保存不可变的会计分录，负责余额和资金流的账务表达。

这些模块共享事件和 PostgreSQL 状态，但没有把所有逻辑塞进 sink worker。这样的边界让高吞吐的用量写入可以独立扩展，也让账单和余额的事务生命周期保持清晰。

小结

本文从本地 Docker Compose 部署开始，完成了事件上报、异步查询、重复事件去重，以及 COUNT、SUM 和维度分组的验证。CloudEvents 统一事件格式，计量器定义统计口径，两者共同把业务中的使用记录变成可以查询的用量。

沿着源码可以看到这条链路的分工：API 接收事件并交给 Kafka，sink worker 消费、去重后写入 ClickHouse，查询接口再根据计量器定义执行聚合；PostgreSQL 则保存计量器和其他业务状态。由于接收与落库分开执行，204 返回后需要等待异步处理完成，才能在查询中看到新增用量。

这次实验覆盖的是计量能力。额度控制、订阅和账单在此基础上继续处理访问权限与费用，各自有独立的模块和生命周期。对于首次接入 OpenMeter 的产品，可以先确认事件字段、使用者归属和计量口径，再根据业务需要加入这些能力。
